# Безопасность и Приватность данных (Security & Privacy)

## 1. Аутентификация и JWT-сессии
* **Реальные учётные записи в БД:** все пользователи и аккаунты организаций проходят регистрацию с сохранением в PostgreSQL. Пароли хешируются алгоритмом `BCrypt` (`BCryptPasswordEncoder`). Пароли никогда не логируются и не возвращаются в DTO.
* **Быстрый переключатель демо-аккаунтов поверх реального JWT:** для удобства демонстрации перед жюри в шапке и на странице `/login` предусмотрен быстрый вход в предзаполненные тестовые аккаунты, который вызывает штатный эндпоинт `POST /api/v1/auth/login` с проверкой `BCrypt`-пароля и выдачей настоящей пары `Access + Refresh` токенов.
* **Двухуровневая модель токенов:**
  * Короткоживущий `Access Token` (`HMAC-SHA256`, по умолчанию 30 минут) содержит `sub`, `email`, `name`, `role` (`USER` или `ADMIN`).
  * Долгоживущий `Refresh Token` (7 дней) хранится в `HttpOnly`, `SameSite=Lax` cookie, а в таблице `refresh_sessions` хранится только его `SHA-256` хеш.
  * **Защита от Replay-атак:** при каждом обновлении (`POST /api/v1/auth/refresh`) старый refresh-токен отзывается. При попытке повторно использовать уже отозванный токен все активные сессии пользователя принудительно аннулируются.
* **Защита роли администратора:** через открытые эндпоинты регистрации невозможно передать или выбрать роль `ADMIN`. Первая учётная запись администратора создаётся контролируемым процессом `DatabaseSeeder` из переменных окружения (`INITIAL_ADMIN_EMAIL` / `INITIAL_ADMIN_PASSWORD`).

## 2. Авторизация на уровне ресурсов (Object-level Authorization)
Проверка прав выполняется на стороне Java backend:
* Рассматривать заявки участников на мероприятие и удалять участников из состава может только автор встречи (`organizer_user_id`), владелец или назначенный со-администратор соответствующего сообщества/организации.
* Аккаунт организации может публиковать мероприятия **только от имени своей организации в статусе `APPROVED`** (создание личных мероприятий и открытых пользовательских сообществ для аккаунтов организаций заблокировано как в UI, так и на уровне `EventService` / `OrganizationService`).
* Запись на завершённые (`COMPLETED`) и прошедшие по времени мероприятия из архива заблокирована (`409 Conflict`).
* Скрытые администратором сообщения (`HIDDEN_BY_ADMIN`) и их вложения исключаются из выдачи обсуждений и блокируются при прямом запросе скачивания файла (`403 Forbidden`).
* При снятии мероприятия с публикации (`UNPUBLISHED_BY_ADMIN`) невозможна запись даже по прямому API-запросу (`409 Conflict`).
* Пользователи имеют доступ только к собственным обращениям (`TCK-XXXXX`), личным сообщениям с друзьями и собственному чату техподдержки (попытка чтения чужого обращения по UUID возвращает `403 Forbidden`).

## 3. Безопасность загружаемых файлов и ссылок
* **Проверка типов и сигнатур (Magic Bytes):** в `FileStorageService` проверяется не только расширение файла из белого списка, но и фактическая сигнатура заголовка файла (блокируются исполняемые файлы `MZ` / `ELF`, проверяются заголовки `%PDF` и `PNG`).
* **Изоляция хранения и защита от Path Traversal:** файлы сохраняются в выделенный Docker volume под сгенерированными именами `UUID`, путь нормализуется (`Path.normalize()`) и проверяется на вхождение в базовую директорию.
* **Безопасная отдача:** файлы отдаются через контроллер `/api/v1/attachments/{id}/content` с заголовком `X-Content-Type-Options: nosniff` и `Content-Disposition: attachment` для документов.
* **Защита от XSS и SSRF:** внешние ссылки валидируются на схему `http://` или `https://` (блокируются `javascript:` и `data:`), открываются с `rel="noopener noreferrer"`, а backend не выполняет автоматических сетевых запросов по пользовательским URL.

## 4. Приватность персональных данных
* Контактные данные представителя организации для связи с модератором (`moderationContact`), пояснения для проверки (`extraModerationInfo`) и черновик правок на модерации (`pendingChangesJson`) возвращаются API **только** владельцу организации и администратору, и никогда не попадают на публичную страницу организации.
* Обезличенные аккаунты организаций автоматически скрыты из поиска спортивных друзей (`showInPartnerSearch = false`). Обычный пользователь сам управляет в настройках профиля флагами видимости в поиске друзей и приватности своих предстоящих записей (`ALL`, `FRIENDS_ONLY`, `NONE`).
