# Архитектурные и продуктовые решения (ADR / Decisions)

В документе зафиксированы ключевые технические и продуктовые решения, принятые при разработке платформы **«Точка Сбора»**.

---

## ADR-001: Монолитный Backend на Java 21 + Spring Boot 3.4 с чётким разделением доменов

- **Контекст:** Платформа объединяет каталог событий, верификацию организаций, медиа-обсуждения, социальный граф, тикеты, живой чат и VK-интеграцию.
- **Решение:** Реализовать модульный монолит на Spring Boot 3.4 (Java 21) с единой базой PostgreSQL 16 и миграциями Flyway.
- **Обоснование:** Обеспечивает строгую транзакционную согласованность (например, при освобождении места на тренировке и автоматическом переводе первого участника из `WAITLISTED` в `APPROVED` с отправкой уведомления) и предсказуемое развёртывание одной командой `docker compose up --build`.

## ADR-002: Безопасная JWT-схема (Access Token в памяти + Refresh Token в HttpOnly Cookie)

- **Контекст:** Хранение долгоживущих токенов в `localStorage` уязвимо к краже при XSS, а чисто сессионная схема усложняет работу SPA и REST API.
- **Решение:**
  - Короткоживущий `accessToken` (15 минут) возвращается в теле ответа и хранится в состоянии клиента.
  - Долгоживущий `refreshToken` (14 дней) устанавливается сервером в `HttpOnly` cookie и хешируется (`SHA-256`) в таблице `refresh_sessions`.
  - При истечении `accessToken` клиентский перехватчик прозрачно вызывает `/api/auth/refresh`.

## ADR-003: Версионирование заявок организаций (`organization_application_history`)

- **Контекст:** В реальном процессе верификации клубов заявка может быть отклонена модератором с указанием причины, после чего представитель исправляет данные и отправляет заявку повторно.
- **Решение:** Вместо перезаписи одного текстового поля создана отдельная таблица `organization_application_history`, фиксирующая каждую итерацию (`versionNumber`, `status`, `adminReason`, `snapshotJson`, `actor`, `createdAt`).
- **Обоснование:** И организатор, и администратор видят полную хронологию: что именно было отправлено в версии #1, почему заявка была возвращена на доработку и что изменилось в версии #2.

## ADR-004: Локальное файловое хранилище в Docker Volume с поддержкой HTTP Range (RFC 7233)

- **Контекст:** В обсуждениях мероприятий пользователи прикрепляют фотографии, документы и видеоролики тренировок. Видео должно перематываться в браузере без скачивания целиком.
- **Решение:**
  - Файлы сохраняются в изолированный Docker volume `uploads_data` (`/app/uploads`) с проверкой MIME-типа и сигнатуры первых байт (magic bytes).
  - Контроллер `AttachmentController` обрабатывает заголовок `Range: bytes=start-end` и отдаёт статус `206 Partial Content` чанками до 1 МБ.

## ADR-005: Двухрежимный контур VK-бота (`TEST_LOG` + `LIVE`)

- **Контекст:** Проверяющий должен иметь возможность протестировать привязку аккаунта по коду `SP-XXXXXX`, команды бота (`/help`, `/my`, `/clubs`, `/unlink`) и доставку уведомлений как без внешних ключей (сразу после `docker compose up --build`), так и с реальным сообществом ВКонтакте.
- **Решение:**
  - В режиме `VK_BOT_MODE=TEST_LOG` (по умолчанию) все исходящие сообщения VK-бота сохраняются в журнал и отображаются в UI на вкладке «VK Бот», а также доступен эмулятор входящего события `message_new`.
  - При указании `VK_BOT_MODE=LIVE`, `VK_GROUP_ID` и `VK_GROUP_TOKEN` тот же сервис работает с реальным `VK Bots Long Poll API` и методом `messages.send`.
