# Архитектурные и продуктовые решения (ADR / Decisions)

В документе зафиксированы ключевые технические и продуктовые решения, принятые при разработке платформы **«Точка Сбора»**.

---

## ADR-001: Монолитный Backend на Java 21 + Spring Boot 3.4 с чётким разделением доменов

- **Контекст:** Платформа объединяет каталог событий, интерактивную карту, раздельные контуры сообществ и организаций, медиа-обсуждения, социальный граф с личными сообщениями, систему обращений, живой чат и VK-интеграцию.
- **Решение:** Реализовать модульный монолит на Spring Boot 3.4 (Java 21) с единой базой PostgreSQL 16 и миграциями Flyway (`V1`–`V6`).
- **Обоснование:** Обеспечивает строгую транзакционную согласованность (например, при освобождении места на тренировке и автоматическом переводе первого участника из `WAITLISTED` в `CONFIRMED` с отправкой уведомления) и предсказуемое развёртывание одной командой `docker compose up --build`.

## ADR-002: Безопасная JWT-схема (Access Token в памяти + Refresh Token в HttpOnly Cookie)

- **Контекст:** Хранение долгоживущих токенов в `localStorage` уязвимо к краже при XSS, а чисто сессионная схема усложняет работу SPA и REST API.
- **Решение:**
  - Короткоживущий `accessToken` возвращается в теле ответа и хранится в состоянии клиента.
  - Долгоживущий `refreshToken` устанавливается сервером в `HttpOnly` cookie и хешируется (`SHA-256`) в таблице `refresh_sessions`.
  - При истечении `accessToken` клиентский перехватчик прозрачно вызывает `/api/v1/auth/refresh`.

## ADR-003: Разделение Сообществ и Организаций + Теневая премодерация изменений (`organization_application_history` и `pending_changes_json`)

- **Контекст:** Любительские беговые или дворовые объединения не должны проходить бюрократическую проверку, тогда как официальные спортивные школы, клубы и федерации требуют верификации администратором. Кроме того, при редактировании описания уже проверенной организации её текущая страница не должна пропадать из каталога на время проверки правок.
- **Решение:**
  - Логически и визуально разделить **Сообщества** (`COMMUNITY`, создаются обычными пользователями и сразу публикуются в `/communities`) и **Организации** (обезличенные аккаунты, публикующие мероприятия строго от имени своей верифицированной организации в `/organizations`).
  - Хранить полную историю первичных подач и повторных отправок в `organization_application_history` (`versionNumber`, `status`, `adminReason`, `snapshotJson`).
  - Для уже одобренных (`APPROVED`) организаций сохранять предлагаемые изменения профиля в поле `pending_changes_json` (`V5__organization_pending_changes.sql`): пока администратор не одобрит или не отклонит правки, всем пользователям продолжает отображаться текущая верифицированная версия карточки.

## ADR-004: Локальное файловое хранилище в Docker Volume с поддержкой HTTP Range (RFC 7233)

- **Контекст:** В обсуждениях мероприятий пользователи прикрепляют фотографии, документы и видеоролики тренировок. Видео должно перематываться в браузере без скачивания целиком.
- **Решение:**
  - Файлы сохраняются в изолированный Docker volume `uploads_data` (`/app/uploads`) с проверкой MIME-типа и сигнатуры первых байт (`magic bytes`).
  - Контроллер `AttachmentController` обрабатывает заголовок `Range: bytes=start-end` и отдаёт статус `206 Partial Content` чанками до 1 МБ.

## ADR-005: Двухрежимный контур VK-бота (`TEST_LOG` + `LIVE`)

- **Контекст:** Эксперты жюри должны иметь возможность протестировать привязку аккаунта по коду `SP-XXXXXX`, команды бота (`/help`, `/my`, `/clubs`, `/unlink`) и доставку уведомлений как автономно без внешних ключей (сразу после `docker compose up --build`), так и с реальным сообществом ВКонтакте.
- **Решение:**
  - В режиме `VK_BOT_MODE=TEST_LOG` (по умолчанию) все исходящие сообщения VK-бота сохраняются в журнал и отображаются в UI на вкладке «Уведомления», где также доступен интерактивный эмулятор входящих команд `message_new`.
  - При указании `VK_BOT_MODE=LIVE`, `VK_GROUP_ID` и `VK_GROUP_TOKEN` тот же сервис работает с реальным `VK Bots Long Poll API` и методом `messages.send`.
